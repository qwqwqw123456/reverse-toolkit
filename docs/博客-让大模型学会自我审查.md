# 我用红队测试思想重构了 AI 逆向工具：让大模型学会"自我审查"

> 一个 Ghidra MCP 工具包，从 17 个工具砍到 5 个原语，并给每条分析结论装上"证据手铐"。
> 仓库：`github.com/qwqwqw123456/reverse-toolkit`（v5.1）

---

## 引子：所有 Ghidra MCP 都死在同一个地方

这两年 Ghidra 的 MCP 封装已经烂大街了——有 200 多个工具的，有把整个 `get_functions()` 结果直接塞进上下文的。
它们的技术栈都很像：Ghidra headless + Python MCP Server + 让模型自己决定下一步。

问题也都很像：

1. **Token 爆炸**。一个中等样本 3000+ 函数，全量伪代码几十 MB，上下文直接崩。
2. **模型降智**。99% 的代码是 `_init`、`register_tm_clones`、`__libc_csu_init`，真正有业务含义的只有十来个。信噪比一低，模型就开始编。
3. **结论不可回溯**。模型说"检测到密码校验逻辑，调用了 strcmp"，你回它一句"哪个函数？地址多少？"——它答不上来，因为它自己也没记住。

第三条才是致命的。前两条是成本问题，第三条是**可信度问题**。

安全分析这个行当，最贵的不是算力，是"你说的话能不能被验证"。

所以 v5.1 只做三件事：**做减法、上证据、请裁判**。

## 一、先做减法：17 个工具砍到 5 个

改造前我的 `mcp_server.py` 里有 17 个 `@mcp.tool()`，README 上写着"15 个可调用工具"。

连文档和代码都对不上——这本身就是工具过载的症状：加工具的时候没人记得回去改文档。

IDA 官方 Code Mode 的经验、REA 那批人的实践，都指向同一个结论：**工具超过 20 个，模型开始选错工具**。
不是模型笨，是"选工具"这一步本身在消耗它最宝贵的推理预算。

v5.1 的 5 个原语，每一个都是"完整业务动作"，不是"一个函数"：

| 原语 | 一个原语干完的事 | 合并掉的旧工具 |
|---|---|---|
| `set_sample(path)` | 锁定样本、重置证据台账 | `set_sample` / `get_context` |
| `run_recon()` | 文件指纹 + 字符串分类 + 敏感导入 + YARA + 风险评级 | `get_overview` / `quick_check` / `get_strings` / `check_imports` / `detect_crypto` / `detect_network` / `scan_threats` / `risk_check` |
| `deep_dive(target)` | 自动脱壳 + Ghidra 反编译 + 伪代码截断 + 交叉引用 | `unpack_binary` / `focus_on_function` / `full_analysis` / `generate_full_report` |
| `extract_threat_intel()` | IOC + YARA + 攻击链 Mermaid | `extract_iocs` / `generate_attack_chain` / `check_antidbg` |
| `audit_and_report(claims)` | 证据裁判 + Markdown 报告 | **新增** |

减法的收益不只是"少选几次"，还顺手修掉了一个老毛病：**跨工具状态断裂**。
以前 `unpack_binary` 返回新路径，模型得自己记住传给下一个工具，忘了就分析了个寂寞。
现在脱壳在 `deep_dive` 内部完成，`active_path` 自动切换，模型根本不需要知道路径变过。

验证方式很土但很有效：

```python
import asyncio, mcp_server as s
print([t.name for t in asyncio.run(s.mcp.list_tools())])
# ['set_sample', 'run_recon', 'deep_dive', 'extract_threat_intel', 'audit_and_report']
```

单测里直接写死断言：**工具数必须是 5**。多一个都算回归。

## 二、证据台账：让每一句话都能被追债

这是整个 v5.1 的地基。

每次工具返回，我都会往一个进程内的"证据台账"里追加一条记录：

```python
_add_evidence(kind, locator, symbol, source, snippet="", truncated=False)
# -> EV-0007 | function | 0x101169 | verify_password | deep_dive
```

然后所有对外输出，一律用 `_tag()` 渲染成统一格式：

```
[Evidence: 0x101169] verify_password
[Evidence: 0x2004]   .rodata: "s3cr3t"
[Evidence: 0x3fd0]   strcmp
```

真实跑一遍 `deep_dive("verify_password")`，输出是这样：

````markdown
### [Evidence: 0x101169] verify_password  (EV-0007)
- 元数据: 48 bytes | xref=4 | [TOP]
- 伪代码（前 60 行）:
```c
bool verify_password(char *param_1)
{
  int iVar1;
  iVar1 = strcmp(param_1,"s3cr3t");
  return iVar1 == 0;
}
```
````

注意，`0x101169` 不是我瞎写的，是 Ghidra 给的入口地址；`"s3cr3t"` 也不是我猜的，是从 `.rodata` 里翻出来的。

### 地址映射：宁可降级，不许编造

这里有个很容易翻车的细节：**文件偏移 ≠ 虚拟地址**。

字符串在文件里的偏移是 0x3515，但它在内存里可能挂在 0x2004。你直接把文件偏移当 VA 输出，就是给自己埋雷。

所以 `_locator_for_offset()` 先用 `readelf -S` 建"节区偏移 → VA"映射表，能算成 VA 就输出 VA；算不出来（比如 `.strtab` 这种非装载节根本没有 VA）就**如实降级**：

```
[Evidence: file+0x3515] .strtab: verify_password
```

带 `file+` 前缀，标明这是文件偏移；带上 `.strtab`，告诉你为什么没有 VA。

这条规则我写进了验收标准：**任何一条地址，要么是真实 VA，要么显式标 `file+`，绝不允许出现第三种。**

### System Prompt：把"引用证据"写进契约

工具给证据是一回事，模型用不用是另一回事。所以 MCP Server 启动时就把契约注入进去：

```python
mcp = FastMCP("Reverse-Toolkit", instructions=SYSTEM_PROMPT)
```

核心那句就是你熟悉的那句：

> 你在得出结论时，必须引用返回结果中的 [Evidence] 标签。如果没有找到证据，请直接说"未找到"。

再加五条配套：截断处不推断、负面结论给检索范围、高危结论必须多源、出报告前必须 `audit_and_report`、区分"已核实 / 推断 / 未找到"。

**光靠 prompt 是不够的。** prompt 是君子协定，模型心情一好就忘了。所以还需要裁判。

## 三、Critic Mode：让工具自己当红队

`audit_and_report(claims)` 是整个 v5.1 里我最满意的部分。

它不生成报告，它先**审判**你的结论。8 条规则：

| 编号 | 规则 | 判定 |
|---|---|---|
| AE-1 | 每条结论至少引用 1 个证据（EV 编号 / 地址 / 符号） | 无证据 → **FAIL** |
| AE-2 | 引用的编号/地址必须存在于本次证据台账 | 不存在 → **FAIL（幻觉）** |
| AE-3 | 结论正文里的 0x 地址必须与台账一致 | 不一致 → **FAIL** |
| AE-4 | 结论提到的函数/API 必须在台账或导入表出现 | 查无实据 → **FAIL** |
| AE-5 | 证据被标记 truncated 时，不得用"确认/必然/完整/证明" | 强推断 → WARN |
| AE-6 | 高危结论不能只靠字符串或 YARA 规则名 | 弱证据 → WARN + 降级"待核实" |
| AE-7 | 多条证据没有共同 token 时，不得写成因果句 | 跨源拼接 → WARN |
| AE-8 | "未找到"结论必须带检索范围证据 | 缺范围 → WARN + 降级 |

真实运行，喂一条幻觉进去：

```
[AUDIT_RESULT: FAIL] 证据链断裂，禁止输出报告。

违规 2 条：
- C9 AE-2: 引用 `0xdeadbeef` 不在证据台账（疑似幻觉地址/编号）
- C9 AE-3: 正文地址 0xdeadbeef 从未在证据台账中出现

## 必须执行的补救动作
1. 对每条 AE-2/AE-4 违规，调用 deep_dive(target_function="...") 重新取证，拿到真实 [Evidence: 地址]；
2. 拿不到证据的结论，改写成『未找到』并附检索范围；
3. 禁止直接输出报告。
```

**关键设计：FAIL 时不写报告文件。**

不是"写个带红字的报告"，不是"输出草稿让人自己判断"，是**根本不落盘**。
单测里直接断言：FAIL 前后新增的 `report_*.md` 数量必须是 0。

这一条比任何 prompt 都硬。模型的幻觉可以很流畅，但它伪造不出一个不存在的地址。

### 只有 PASS 才配拿到报告

同样的会话，换成真实证据：

```
[AUDIT_RESULT: PASS] 结论 2 条 · 违规 0 · 警告 0 · 证据 9 条
报告文件: /tmp/rea_v51/v51_sample_.../report_v51_final_check_*.md
```

报告里的每条结论都长这样：

| # | 结论 | 证据 | 判定 |
|---|---|---|---|
| C1 | verify_password 通过 strcmp 与硬编码口令 s3cr3t 比较，返回 0 时放行 | `[Evidence: 0x101169] verify_password`; `[Evidence: 0x3fd0] strcmp` | PASS |
| C2 | 未找到反调试逻辑 | `[Evidence: 0x101169] verify_password` | PASS |

看到 C2 了吗？"未找到"也是一种结论，也需要证据——证明你确实查过那个范围。
这比"什么都没找到所以不写"高级：**空结论也要有证据支撑**。

## 四、柔性降级：WARN 比 FAIL 更难写

一刀切 FAIL 是最省事的设计，也是最没用的设计。

真实逆向里大量结论是"有依据但不够硬"：

- 伪代码导出了 60 行，函数有 200 行，后面截断了，模型说"该函数完整实现了 RC4"——这是**截断处强推断**（AE-5）。
- 只从字符串里看到 `ransom`、`bitcoin`，就判定"这是勒索软件"——这是**弱证据**（AE-6）。
- 一条证据说"有 socket"，另一条说"有 base64 表"，模型写成"socket 传的是 base64 编码的 C2"——这是**跨源因果**（AE-7），两条证据之间根本没有共同 token。

这三种情况我的处理是：

```
[WARN] AE-6: 高危结论仅靠字符串支撑，已自动降级为「待核实」
```

**降级，不删除；标注，不改写。**

因为安全分析里有价值的往往就是这些"半成品线索"。裁判的职责是把"已核实"和"推测"分开，不是把所有不确定的东西都扔进垃圾桶。

## 五、FOCUS：Top N 之外的那个函数

这条是踩坑踩出来的。

`ExportDecompiled.java` 的降噪逻辑是：黑名单剔除 CRT 噪声 → 危险 API 加权 → 交叉引用加权 → 取 Top 50 → 补一层 callees。

听起来很合理，直到我遇到这个场景：

```
_index.txt 里有 verify_password      ← 索引命中了
decompiled/ 里没有 verify_password.c ← 伪代码没导出
```

原因很简单：那个函数 xref=0，压根没进 Top 50。模型看到索引里有名字，去读伪代码，读了个空，然后开始"合理推测"。

修复方案是给脚本加第 3 个参数 `focus`，在 Top-N 收集之后、导出之前插一段强制导出：

```java
// v5.1: 聚焦导出 —— 目标函数不在 Top N 时强制加入
if (!focus.isEmpty()) {
    String fLow  = focus.toLowerCase();
    String fAddr = fLow.startsWith("0x") ? fLow.substring(2) : fLow;
    for (Function f : allFuncs) {
        boolean nameHit = f.getName().toLowerCase().contains(fLow);
        boolean addrHit = f.getEntryPoint().toString().toLowerCase().contains(fAddr);
        if (nameHit || addrHit) { toExport.add(f); funcLayer.put(f, "[FOCUS]"); }
    }
}
```

实测：75 个符号函数，`zz_target` 没有任何调用者，Top 50 永远轮不到它：

```
### [Evidence: 0x10206e] zz_target  (EV-0005)
- 元数据: 26 bytes | xref=3 | [FOCUS]
- 伪代码:
    int zz_target(int param_1)
    {
      return param_1 * 7 + 3;
    }
```

`[FOCUS]` 这个层标记，就是"我知道它排不上号，但我就是要看它"的证明。

透视一下整条链：

```
deep_dive("verify_password")
  → focus_func.sh 传 "$FOCUS"
  → ghidra.sh     传 "${FOCUS_KEYWORD:-}"
  → ExportDecompiled.java <outDir> <topN> <focus>
```

只改了两行 shell，但把"降噪"和"不漏关键函数"这对矛盾解开了。

## 六、我在实现里踩的 6 个坑（这部分才是真货）

写代码时最花时间的不是架构，是这些细节：

| 坑 | 现象 | 修法 |
|---|---|---|
| 字符串证据 symbol 重复 | `[Evidence: 0x2004] s3cr3t: "s3cr3t"` | 改成 `节区名: 字面量`，字面量只出现一次 |
| `.strtab` 没有 VA | 输出了个 `?` 当地址 | 降级 `file+0x...`，并带上节区名 |
| Ghidra 的字符串带 `u8"..."` 前缀 | 按字面量查偏移永远查不到 | `_literal_variants()` 逐个变体试：去前缀、去引号、反转义 |
| `_index.txt` 末列粘连 | `xref=4[TOP]` 被当成一个字段 | 正则分别提取 `xref=\d+` 和 `[TOP/CALLEE/FOCUS/DANGEROUS]` |
| 四个字符串分类文件互相重复 | 同一个 URL 在 URL 类和基础类里各出现一次 | 加 `seen` 集合去重 |
| `strcmp` 不在敏感导入名单 | 密码校验样本居然"没有导入证据" | 补 `strcmp/strncmp/memcmp`——认证逻辑的核心信号 |

还有两个裁判自己的 bug：

- AE-1 和 AE-2 重复报同一条问题（没证据 + 引用了不存在证据）。改成"只有完全没写 evidence 字段才报 AE-1"。
- AE-4 去校验 0x 地址，跟 AE-3 撞车。改成地址一致性只归 AE-3，AE-4 只管符号。

**幻觉不是靠"多写几条规则"解决的，是靠"每条规则只判定它该判定的事"。**

## 八、这个版本不做什么

说清楚边界，比吹功能重要：

- **不做全量伪代码导出**。想看全集自己用 Ghidra，MCP 的职责是"挑出值得看的 50 个"。
- **不做语义级漏洞判定**。排序只基于静态特征（API / xref / 体积），不猜业务。
- **不假装扫过**。YARA/UPX 没装就降级成 strings 特征，报告里明写"已降级"。
- **不兼容旧工具名**。17 个旧名字全删了。留别名等于留选择困难，5 个原语才是这套架构的边界。

## 结语：防幻觉不是 prompt 玄学，是账本 + 裁判 + 不落盘

如果只让我留一句话：

> **让模型说错话的代价，高于让它说"未找到"的代价。**

具体落地就是三件事：

1. **账本**——每条结论绑定一个真实地址，地址从二进制里来，不从模型嘴里来。
2. **裁判**——8 条规则只管"证据与声明是否匹配"，不评价结论好坏。
3. **不落盘**——FAIL 的时候，连一个 Markdown 文件都不给。

这三样凑齐，你的工具才从"一个方便的脚本"变成"具备可信度审计能力的分析助理"。

而 `ExportDecompiled.java` 那个降噪脚本，我建议单独开源——
因为它解决的"几千个函数怎么压成 20 个"，是所有 Ghidra MCP 的共同痛点。
你打不过 REA，但你可以成为 REA 用户顺手装上的那个增强件。
